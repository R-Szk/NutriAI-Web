# NutriAI かんたん食品・標準レシピ設計

作成日: 2026-10-26

## 目的

文部科学省食品成分データの詳細な食品名を利用者が毎回判断する負担を減らし、普段食べる食品や料理を数秒で記録できるようにする。

栄養値は引き続き食品データベースを正とする。AIが栄養値を生成する方式にはせず、分かりやすい表示名、標準量、標準レシピを既存の文科省食品へ対応付ける。

本機能では、完全な精度より日常的な記録のしやすさを優先する。ただし、目安の重量や標準レシピであることを明示し、計算根拠を確認できる状態を保つ。

## 成功条件

- 「納豆」などの検索で、一般的な候補を迷わず選べる。
- 「1パック」「1膳」「1枚」「1皿」など日常的な単位で記録できる。
- 日常的な単位には計算に使うグラム数も併記される。
- 単品食品と複数材料の料理を、同じ分かりやすい操作で記録できる。
- 食事一覧には材料の羅列ではなく、利用者が選んだ食品名・料理名が表示される。
- 栄養計算は既存の `foods` / `food_nutrients` を基準に行われる。
- 現在の詳細な文科省食品検索も利用できる。

## 設計方針

- 文科省データを栄養値の土台として維持する。
- その上に、NutriAIが管理する「かんたん食品」と「標準レシピ」を追加する。
- 標準量と栄養値の出典を区別して管理する。
- 単品食品も料理も、画面では利用者が記録した一つの項目として扱う。
- 栄養計算用には、一つ以上の文科省食品と重量へ分解する。
- 標準量や料理のカロリーには、必要に応じて「約」を付ける。
- 初回リリースの品目を絞り、動作を確認してから増やす。
- 将来の写真入力は食品・料理候補を選ぶ補助とし、栄養値の正にはしない。

## 採用しない方式

### TypeScriptへの固定一覧

初期実装は単純だが、品目追加のたびにコード変更とデプロイが必要になる。複数材料の料理や出典管理にも向かないため採用しない。

### AIによる動的な栄養値生成

同じ入力でも結果が変わる可能性があり、値の根拠を追跡できない。NutriAIのデータ方針に反するため採用しない。

## マスターデータ

### `food_serving_presets`

単一食品に対する、利用者向けの表示名と標準量を管理する。

主な情報は次のとおりとする。

| 情報 | 用途 |
|---|---|
| 表示名 | 「納豆」「ご飯」など利用者向けの名称 |
| 検索キーワード | 別名や検索時に一致させる語句 |
| 参照食品 | `foods` の1行 |
| 標準重量 | 栄養計算に使うグラム数 |
| 表示単位 | 「1パック」「1膳」「1枚」など |
| 表示優先度 | 検索結果の並び順 |
| 根拠の説明 | 重量を決めた理由やNutriAI独自の目安であること |
| 参考URL | 公的資料やメーカー情報など、存在する場合の参照先 |
| 有効状態 | 一時的に検索結果から外せる状態 |
| 更新日時 | 根拠を見直した時期 |

栄養値そのものは保存しない。参照食品の100g当たり栄養値を標準重量へ比例換算する。

同じ食品に複数の量候補がある場合は、代表候補を一つ指定したうえで追加候補を関連付ける。例えばご飯では「普通盛り150g」を代表候補とし、「小盛り100g」「大盛り200g」を量選択に表示する。納豆の「2パック」は別の栄養データを持たず、代表候補45gへ数量2を掛けて90gとする。

実装時には、固定重量の追加候補を管理する子テーブルを設ける。子テーブルは表示名、重量、表示順を持ち、親の参照食品と出典を共有する。これにより、量候補を追加するためだけに画面コードへ数値を埋め込まない。

### `standard_recipes`

複数の食品から構成される標準料理を管理する。

主な情報は、料理名、検索キーワード、表示単位、説明、表示優先度、根拠、参考URL、有効状態、更新日時とする。

例:

```text
料理名: カレーライス
表示単位: 1皿
説明: NutriAI標準レシピ
```

### `standard_recipe_items`

標準レシピを構成する `foods` と、1食分の重量を管理する。

```text
カレーライス 1皿
├─ ご飯 200g
├─ 肉（食品と重量は初期データ調査で確定）
├─ 玉ねぎ（同上）
├─ にんじん（同上）
├─ じゃがいも（同上）
└─ カレールー（同上）
```

料理の栄養値は、各材料の100g当たり栄養値を材料重量へ換算し、その結果を栄養素ごとに合計する。

## 食事記録データ

現在の `meal_items` は一つの文科省食品とグラム数を直接保存する。料理を材料ごとにこのテーブルへ保存すると、画面に材料が個別表示され、同じ食品を別の用途で追加した際に一意制約による上書きが起こり得る。

そのため、利用者が記録した単位と栄養計算用の構成食品を分離する。

### `meal_entries`

利用者が選択した一つの記録を表す。

例:

```text
表示名: カレーライス
数量: 1
単位: 皿
登録元: standard_recipe
```

単品食品の場合も同じ形で、「納豆・1・パック」のように保存する。登録時点の表示名と単位を保持し、後からマスター名が変更されても過去の記録表示が意図せず変化しないようにする。

### `meal_entry_components`

一つの `meal_entries` に含まれる計算用食品と重量を保持する。

```text
納豆 1パック
└─ 糸引き納豆 45g

カレーライス 1皿
├─ ご飯 200g
├─ 豚肉 40g
└─ その他の材料
```

栄養値の計算結果は保存せず、構成食品と重量から都度計算する。表示名などは記録時点の値を保持するが、栄養値は既存方針どおり食品DBを参照する。

単品の詳細な文科省食品を直接選んだ場合も、`meal_entries` 1行と `meal_entry_components` 1行へ統一して保存する。

## 検索と選択のUI

検索結果は次の順で表示する。

### おすすめ

`food_serving_presets` と `standard_recipes` から、検索語に一致する代表候補を最大5件表示する。

```text
おすすめ

納豆
1パック（45g）・約83kcal
```

料理の場合は次のように表示する。

```text
カレーライス
標準1皿・約［確定した標準レシピから算出した値］kcal
```

### 量の変更

選択後、代表的な量をボタンで選べるようにする。任意のグラム数も入力できる。

```text
納豆
[1パック 45g] [2パック 90g] [量を入力]

ご飯
[小盛り 100g] [普通 150g] [大盛り 200g]
```

単位名だけで重量が一意に決まらない食品では、必ずグラム数を併記する。

### 詳しい食品

現在の文科省食品検索結果は、おすすめの下へ折りたたんで表示する。

```text
詳しい食品を見る（6件）

・糸引き納豆
・挽きわり納豆
・五斗納豆
・寺納豆
```

詳細食品を選んだ場合は、現在と同様に任意の摂取量を入力できる。

## 保存と表示の流れ

1. 利用者が日付と食事区分を指定して食品追加画面を開く。
2. かんたん食品、標準レシピ、または詳細食品を検索する。
3. 標準量または任意量を選択する。
4. 選択内容を一つの `meal_entries` として保存する。
5. 計算用食品と重量を `meal_entry_components` に保存する。
6. 保存成功後、選択日のダッシュボードへ戻る。
7. 食事一覧には `meal_entries` の表示名、数量、単位を表示する。
8. 1日の栄養合計は `meal_entry_components` から計算する。

複数行を必要とする保存は、途中状態を残さないようPostgreSQL関数とRPCによるトランザクションを基本とする。

## 初期ラインナップ

### 単品・主食

- ご飯: 普通盛り150g
- 納豆: 1パック45g
- 食パン: 6枚切り1枚。採用する計算重量を調査して明記する
- 絹ごし豆腐: 1/2丁150g
- 卵: 1個。採用する可食部重量を調査して明記する
- バナナ: 1本。採用する可食部重量を調査して明記する
- 牛乳: コップ1杯200ml。食品DBの重量換算方法を明記する
- ヨーグルト: 1個または100g。採用量を調査して明記する

### 標準料理

- カレーライス: 1皿
- 味噌汁: 1杯
- 親子丼: 1杯

初期料理は3品に限定し、検索、保存、再表示、栄養合計が正しく動くことを優先する。

## 数値と出典のルール

- 文科省に単品データがある場合は、その100g当たりの値を使用する。
- 個数、枚数、パック数の重量は、公的資料またはメーカー情報を確認する。
- 商品差が大きい場合は、画面に計算重量を併記する。
- 標準料理は材料と重量を明記したNutriAI標準レシピとして管理する。
- NutriAI独自の目安はその事実を明記する。
- 根拠を確認できない数値は登録しない。
- AIは候補の提示に利用できるが、重量や栄養値を自動的に補完しない。

## 欠損値

栄養値が `not_measured`、`missing`、`reference` などで数値を持たない場合は、ゼロとして扱わない。

- 一部材料だけ値が欠損する場合: 既知値を合計し、欠損を含むことを示す。
- 全材料で値が欠損する場合: 「データ無し」と表示する。

既存の `hasKnownValue` と `hasMissingValue` の考え方を、新しい構成食品の集計でも維持する。

## RLSと権限

かんたん食品と標準レシピのマスターは全利用者が読み取れるようにし、ブラウザからの追加・更新・削除は許可しない。現在の食品マスターと同じ読み取り専用方針を採用する。

`meal_entries` と `meal_entry_components` はユーザー固有データとする。親の `meals.user_id` が `auth.uid()` と一致する場合だけ、SELECT、INSERT、UPDATE、DELETEを許可する。

保存用RPCでも認証ユーザーをDB側で確認し、クライアントから渡された別ユーザーのIDを信用しない。

## エラー処理

- 標準量が未設定の場合は、グラム入力へ切り替える。
- 無効化されたプリセットやレシピは検索結果に表示しない。
- 構成食品が欠損しているレシピは保存せず、データ不備を表示する。
- 複数行の保存に失敗した場合はトランザクション全体をロールバックする。
- 栄養値の欠損はゼロへ変換しない。
- 検索エラー時も入力した検索語を維持し、再試行できるようにする。
- 既存データ移行で変換不能な行があれば削除せず、処理を中断して対象を確認する。

## 既存データの移行

旧 `meal_items` は新構造の稼働直後には削除しない。

1. 新しいマスターと食事記録テーブルを追加する。
2. 既存 `meal_items` 1行を、`meal_entries` 1行と `meal_entry_components` 1行へ変換する。
3. 移行前後の件数、食品ID、重量、日次栄養合計を比較する。
4. 保存、取得、表示、合計計算を新構造へ切り替える。
5. ブラウザとDBで動作確認する。
6. 安定確認後、旧テーブルの整理を別マイグレーションで行う。

移行は再実行しても重複しない方法とし、変換途中の状態を残さない。

## テスト方針

### 純粋関数

- 検索語とキーワードの一致を判定できる。
- おすすめ候補を優先度順に並べられる。
- 単品の標準重量から栄養値を計算できる。
- 複数材料の栄養値を栄養素ごとに合計できる。
- 一部または全部が欠損した栄養値をゼロと判定しない。
- 数量変更に応じて各構成食品の重量を変更できる。

### DBとRLS

- かんたん食品と標準レシピを匿名認証ユーザーが読み取れる。
- ブラウザからマスターを変更できない。
- 自分の `meal_entries` と構成食品だけを操作できる。
- 他ユーザーの記録を取得・変更できない。
- RPCの途中でエラーが起きた場合に一部だけ保存されない。

### 移行

- 既存記録の件数と重量が新構造へ引き継がれる。
- 移行前後の日次栄養合計が一致する。
- 移行を再実行しても記録が重複しない。

### ブラウザ

- 「納豆」で一般的な納豆が先頭に表示される。
- 納豆1パックが45gとして計算される。
- ご飯の量候補を切り替えられる。
- カレー1皿が一つの料理として保存・表示される。
- カレーの構成材料から栄養合計を計算できる。
- 詳細な文科省食品も引き続き選択できる。
- 保存後に対象日のダッシュボードへ戻り、最新の記録が表示される。

## 段階的な実装

1. 初期品目の参照食品、標準重量、標準レシピと出典を確定する。
2. かんたん食品・標準レシピのマスターを追加する。
3. 新しい食事記録構造と保存RPCを追加する。
4. 既存記録を新構造へ移行し、整合性を検証する。
5. 検索結果を「おすすめ」と「詳しい食品」に分ける。
6. 標準量の選択と料理の保存を実装する。
7. 食事一覧と日次栄養合計を新構造へ切り替える。
8. 自動テスト、RLS確認、ESLint、production build、スマートフォン表示を確認する。
9. 安定確認後、旧 `meal_items` の整理を別タスクとして検討する。

## 今回の対象外

- 写真認識
- バーコード検索と市販商品DB
- AIによる料理や栄養値の自動生成
- ユーザー独自の「いつもの食事」編集画面
- 一般ユーザーが標準レシピを投稿する機能
- 旧 `meal_items` の即時削除

## 将来拡張

- 利用者が標準量を変更して「いつもの量」として保存する。
- 標準レシピを複製して自分のレシピを作る。
- バーコードからメーカー公表値を持つ商品を選択する。
- 写真AIが、既存のかんたん食品、標準レシピ、商品から候補を提示する。
- 利用履歴から候補の順番を個人最適化する。

写真AIを追加した場合も、最終的な栄養計算は本設計の食品・レシピ・構成食品を通して行う。
