# NutriAI モバイルダッシュボード UI/UX設計

作成日: 2026-10-10

## 目的

Phase 1で完成した食品検索、食事保存、日別記録、栄養合計の機能を保ったまま、スマートフォンを中心に使いやすい画面へ再構成する。

ダッシュボードでは「今日の栄養状態」と「どの食事で何を食べたか」をひと目で確認できるようにする。食品検索は専用画面へ分離し、記録するときだけ検索操作へ集中できる構成とする。

## 設計方針

- スマートフォン表示を基準に設計し、広い画面では中央寄せと最大幅を設定する。
- ダッシュボード案Aの栄養サマリーを基本とする。
- 食事一覧には案Cの時系列表現を取り入れる。
- 食品検索はダッシュボードへ常時表示せず、専用ページへ分離する。
- 既存の検索、栄養計算、Supabase保存処理は再利用する。
- 現在は栄養の実績値だけを表示し、将来は目標値との比較を追加できる構造にする。
- 栄養目標の仮データは埋め込まない。

## 画面構成

### `/` ダッシュボード

選択日の栄養状態と食事記録を確認するメイン画面とする。

上から次の順に配置する。

1. アプリヘッダー
2. 日付選択
3. 1日の栄養サマリー
4. 食事タイムライン

#### アプリヘッダー

- アプリ名「NutriAI」
- 短い説明文
- 将来ナビゲーションを追加できる余白を残す

#### 日付選択

- 初期値はブラウザのローカル日付とする。
- 過去日や別の日付へ変更できる。
- 日付変更時は、その日の栄養合計と食事記録を再取得する。

#### 栄養サマリー

主要栄養素をカード形式で表示する。

- エネルギー
- たんぱく質
- 脂質
- 炭水化物

現在は実績値のみを表示する。将来、利用者ごとの目標値を実装したときは、同じ領域を次の形式へ拡張する。

```text
実績 / 目標
1,650 / 2,000 kcal
```

目標に対する進捗バーも追加できる構造とする。ただし、今回のUI改善では目標値や仮の進捗率を実装しない。

栄養データがすべて欠損している場合は「データ無し」と表示する。一部だけ欠損している場合は既知値の合計を表示し、注意文を添える。

#### 食事タイムライン

次の4区分を常にこの順番で表示する。

1. 朝食
2. 昼食
3. 夕食
4. 間食

DBに記録がない区分も省略しない。記録がない場合は「まだ記録がありません」と「食品を追加」ボタンを表示する。

各区分には次を表示する。

- 食事区分の日本語名
- 登録食品の名称
- 摂取量
- 主要栄養素
- 「食品を追加」ボタン

タイムラインの線やマーカーは情報の順序を補助する装飾として使用し、色だけに意味を持たせない。

### `/record` 食品追加

食品の検索、選択、摂取量入力、栄養計算、保存に集中する画面とする。

上から次の順に配置する。

1. ダッシュボードへ戻る操作
2. 追加先の日付と食事区分
3. 食品検索フォーム
4. 検索結果
5. 選択食品と摂取量入力
6. 計算された主要栄養素
7. 保存操作

追加先はURLのクエリパラメーターで受け取る。

```text
/record?date=2026-10-10&mealType=breakfast
```

- `date`: `YYYY-MM-DD`形式の日付
- `mealType`: `breakfast`、`lunch`、`dinner`、`snack`のいずれか

内部値には既存の英語コードを使い、画面上では日本語へ変換する。

クエリパラメーターが不正な場合は、不正値をそのまま保存へ渡さない。安全な初期値へ戻すか、ダッシュボードから追加先を選び直す案内を表示する。

## 画面遷移

```text
ダッシュボード
  ↓ 各食事区分の「食品を追加」
食品追加画面
  ↓ 検索・選択・摂取量入力・保存
選択していた日付のダッシュボード
```

保存成功後は、保存した日付を維持した状態でダッシュボードへ戻す。戻った画面では最新の食事記録と栄養合計が表示されるようにする。

保存に失敗した場合は食品追加画面に留まり、入力内容をできるだけ維持してエラーを表示する。

## コンポーネント構成

| ファイル | 役割 |
|---|---|
| `src/app/page.tsx` | ダッシュボードページ |
| `src/app/record/page.tsx` | 食品追加ページ |
| `src/components/nutrition-dashboard.tsx` | 日付、匿名認証、日別データの再取得を調整 |
| `src/components/daily-nutrition-summary.tsx` | 1日の主要栄養素を表示 |
| `src/components/meal-timeline.tsx` | 4つの食事区分を時系列に配置 |
| `src/components/meal-section.tsx` | 1区分の食品一覧、空状態、追加操作を表示 |
| `src/components/food-search.tsx` | 食品検索、選択、摂取量、栄養計算を担当 |
| `src/components/meal-save-form.tsx` | 選択した日付と食事区分への保存を担当 |

現在の `DailyMealRecords` が持つ役割は、日別データ取得、栄養サマリー、食事一覧に分離する。分割後もSupabaseアクセスと栄養計算の既存ロジックを再利用する。

コンポーネント名や境界は実装時に既存コードとの重複を確認して最終決定する。見た目だけを理由にデータ取得を複数箇所へ重複させない。

## 状態とデータの流れ

### ダッシュボード

1. 匿名セッションを復元または作成する。
2. 選択日をローカル日付で初期化する。
3. ユーザーIDと選択日を使って食事記録を取得する。
4. 取得した同一データから栄養合計と食事タイムラインを生成する。
5. 日付変更時に対象日のデータを再取得する。

栄養サマリーと食事タイムラインが別々に同じデータを取得する構造にはせず、親で取得した日別データをpropsで渡す構造を基本とする。

### 食品追加

1. URLから日付と食事区分を取得して検証する。
2. 食品を検索する。
3. 食品を選択する。
4. 摂取量を入力して主要栄養素を計算する。
5. 日付、食事区分、食品ID、摂取量を保存する。
6. 保存成功後に対象日のダッシュボードへ戻る。

## レスポンシブ方針

- 最小幅320px程度でも横スクロールが発生しないようにする。
- 本文はスマートフォンで読みやすい左右余白を設ける。
- タップ対象は十分な高さを確保する。
- 入力欄と主要ボタンはスマートフォンでは原則として横幅いっぱいにする。
- PCではコンテンツに最大幅を設けて中央に配置する。
- 栄養カードは狭い画面では2列を基本とし、極端に狭い場合も文字が重ならないようにする。

## 状態表示

各画面で次の状態を明確に区別する。

- 匿名認証の準備中
- データ読み込み中
- データがない状態
- 検索結果がない状態
- 入力値が不正な状態
- Supabase通信エラー
- 保存中
- 保存成功

ボタンを無効化するだけでなく、なぜ操作できないのかが必要な場面では説明を表示する。

## アクセシビリティ

- 入力欄には視覚表示またはスクリーンリーダー用のラベルを関連付ける。
- 選択状態は色だけでなく `aria-pressed` などでも伝える。
- フォーカス位置が分かる表示を維持する。
- 戻る操作や追加操作には、対象の日付・食事区分が理解できる文言を付ける。
- 読み込みや保存結果は、必要に応じて支援技術へ伝わる方法を検討する。

## 今回の対象外

- 利用者ごとの栄養目標設定
- 目標に対する進捗率の計算
- AIによる栄養フィードバック
- 食事記録の削除
- 複数画面を横断する本格的な下部ナビゲーション
- PWA対応

これらを将来追加しても、ダッシュボードの栄養サマリーと食事タイムラインを大きく作り直さずに済む構造を目指す。

## 受け入れ条件

- スマートフォン幅でダッシュボードの主要情報が横スクロールなしで表示される。
- 1日の栄養合計が食事一覧より前に表示される。
- 朝食、昼食、夕食、間食が、記録の有無にかかわらず常に表示される。
- 各食事区分から、その日付と区分を引き継いで食品追加画面へ移動できる。
- 食品検索、食品選択、摂取量計算、保存が既存と同様に動作する。
- 保存成功後に対象日のダッシュボードへ戻り、保存内容が表示される。
- 過去日を選択して食品を追加した場合も、その過去日に保存される。
- 不正な日付や食事区分を保存処理へ渡さない。
- 既存の自動テスト、ESLint、production buildが通る。
