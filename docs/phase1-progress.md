# Phase 1 開発進捗

最終更新日: 2026-09-23

## Phase 1の目標

NutriAIのPhase 1では、次の流れを完成させる。

```text
食品を検索
→ 食品を選択
→ 摂取量を入力
→ 栄養量を計算
→ 朝食・昼食・夕食・間食として保存
→ 1日の栄養合計を表示
→ ページを再読み込みしても記録が残る
```

現在は「摂取量から栄養量を計算する」ところまで実装済みで、次は食事記録の保存へ進む。

### 食品データベース

次の3テーブルを作成した。

- `foods`: 食品の基本情報
- `nutrients`: 栄養素の定義、単位、表示順

食品と栄養値は公開読み取り専用とし、RLSでブラウザからの書き込みを禁止している。DB変更は次のmigrationに保存している。

- `supabase/migrations/20260906000000_create_food_tables.sql`
- `supabase/migrations/20260921000000_add_reference_nutrient_status.sql`

取り込み結果:

2,538 × 53 = 134,514

- `scripts/mext-nutrients.ts`: 栄養素定義
- `scripts/mext-value.ts`: 文部科学省の値表記をDB用に変換

### 栄養値の特殊表記

文部科学省データの元表記を `raw_value` に残し、アプリで扱う状態を `value_status` に保存する。

| 元表記 | `amount` | `value_status` |
|---|---:|---|
| `12.3` | 12.3 | `measured` |
| `(12.3)` | 12.3 | `estimated` |
| `0` | 0 | `zero` |
| `(0)` | 0 | `estimated` |
| `Tr` | 0 | `trace` |
| `(Tr)` | 0 | `estimated_trace` |
| `-` | null | `not_measured` |
| 空欄 | null | `missing` |
| `*` | null | `reference` |

注記記号付きの数値も、注記を `raw_value` に残したまま数値へ変換する。

### 食品検索

`src/components/food-search.tsx` にClient Componentとして実装した。

- 食品名の部分一致検索
- 文部科学省データだけを検索対象に限定
- 食品コード順に最大20件表示
- 検索中、0件、エラーの状態表示
- 空白だけの検索を拒否
- 検索結果から食品を1件選択
- 選択中の食品を緑色で表示
- 選択中の食品を再度押すと解除
- `aria-pressed` による選択状態の伝達

### 摂取量入力と栄養計算

- 食品選択時に100gを初期値として設定
- 正数と小数の摂取量を受け付ける
- 空欄、0、負数、数値以外、Infinityを拒否
- 食品選択解除や再検索で入力・計算結果をリセット
- 選択食品の53栄養素をSupabaseから取得
- `is_primary = true` の主要4栄養素を表示

表示する主要栄養素:

- エネルギー
- たんぱく質
- 脂質
- 炭水化物

計算式:

```text
100g当たりの栄養値 × 摂取量(g) ÷ 100
```

確認例:

| 栄養素 | 100g | 150g |
|---|---:|---:|
| エネルギー | 343 kcal | 514.5 kcal |
| たんぱく質 | 12.7 g | 19.05 g |
| 脂質 | 6 g | 9 g |
| 炭水化物 | 64.9 g | 97.35 g |

### 食事記録と匿名認証

Supabaseの匿名認証を使い、ログイン画面なしで利用者ごとの食事記録を分離した。

- 既存セッションがあれば同じ匿名ユーザーを復元
- セッションがなければ匿名ユーザーを作成
- React Strict Modeによる初期化処理の再実行でも、ユーザーを二重作成しない
- 記録日はブラウザのローカル日付を初期値とし、過去日へ変更可能
- DBには `breakfast` / `lunch` / `dinner` / `snack` を保存し、画面では日本語表示

食事記録には次の2テーブルを使用する。

| テーブル | 役割 |
|---|---|
| `meals` | ユーザー・日付・食事区分ごとの食事枠 |
| `meal_items` | 食事に含まれる食品と摂取量 |

`(user_id, meal_date, meal_type)` と `(meal_id, food_id)` の一意制約を利用してupsertする。同じ日・食事区分・食品を保存し直した場合は行を増やさず、既存の `amount_g` を置き換える。100gから150gへ再保存し、同じ `meal_id` と `meal_item_id` のまま摂取量だけが更新されることを確認した。

RLSでは、`meals.user_id` が `auth.uid()` と一致する行だけを操作できる。`meal_items` は親の `meals` を参照して所有者を判定する。

匿名ユーザーBのJWT claimsと `authenticated` ロールを設定して、匿名ユーザーAの記録へアクセスするRLS確認を行った。Aの `meals` と `meal_items` はどちらも0件として返り、Aの `meals` に対するUPDATEも0件だった。

### 選択日の記録と栄養合計

- 選択日の `meals` から、`meal_items`、`foods`、`food_nutrients`、`nutrients` をnested selectで取得
- 朝食・昼食・夕食・間食の順に表示
- 保存成功後に一覧を自動再取得
- 日付変更時に対象日の記録へ切り替え
- ページ再読み込み後も匿名セッションと記録を復元
- 主要栄養素を100g当たりの値と摂取量から都度計算
- 複数食品の値を合計して1日の主要栄養素を表示

未測定などの `NULL` は数値0として扱わない。一部の食品だけ値が欠ける場合は既知値の合計と注意を表示し、すべて欠ける場合は「データ無し」と表示する。
